* New `packages/registry/spidermonkey/node-upstream/builtin-compiler.cpp/.h` exists in that commit, but no recipe/patch reference wires it to a Mozilla build. A successful unchanged `spidermonkey` package build would therefore **not compile this new code**.

Its successful old builds/configuration cannot silently stand in for the clean branch recipe. Selecting caches/build flags from that campaign would need explicit source/ABI/toolchain reconciliation and would not itself verify the new branch.

The new compiler requires real public API signatures from `mozilla/Utf8.h`, `js/{CompilationAndEvaluation,CompileOptions,EnvironmentChain,ErrorReport,Modules,SourceText}.h`, plus the registry header. These transitively need generated build state: `js/src/jstypes.h:30-32` includes **`js-config.h`** unconditionally; `js/src/moz.build:91-109` declares configure-generated **`js-confdefs.h` / `js-config.h`** and exports; `moz.build:115-116` includes generated `js/PrefsGenerated.h`. Bare source headers or guessed defines are not equivalent to this target's configured export tree.

## Why normal cache resolution does not preserve an incremental object tree

`tools/xtask/src/build_deps.rs:12316-12382` creates private SourceOnly recipe/source-input work roots. `14350-14367` explains these are separate from the atomic published output and cleaned on return. The script uses `WASM_POSIX_DEP_WORK_DIR/{spidermonkey-source,obj-wasm32,...}` (`build-spidermonkey.sh:28-53` at the restart commit); its public output contract only publishes `js.wasm` and `node.wasm` (`:403-446`). The shared cache is an installed-output cache, **not a SpiderMonkey development-header/object cache**.

No hidden alternate Git checkout is needed to preserve package scratch: normal package work directories are explicitly allowed. What cannot be bypassed is selecting the correct reviewed checkout/recipe and declaring the new source/generator inputs before asking the normal resolver to build it.
