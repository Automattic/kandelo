# WEBKIT-TEXTDECODER-WRAPPER-CRASH

Status: suspected. No standalone reduction crashes yet. Not filed.

## Defect

Suspected WebKit defect. The WebKit page process (WebContent) crashed with
`EXC_BAD_ACCESS` / `SIGSEGV` while JavaScript constructed a `TextDecoder`
in a dedicated worker:

```
WTF::HashTable<void*, KeyValuePair<void*, JSC::Weak<JSC::JSObject>>, ...>::add / inlineSet
WebCore::cacheWrapper<WebCore::TextDecoder, WebCore::JSTextDecoder>(DOMWrapperWorld&, TextDecoder*, JSTextDecoder*)
WebCore::toJSNewlyCreated(JSGlobalObject*, JSDOMGlobalObject*, Ref<TextDecoder>&&)
WebCore::JSDOMConstructor<WebCore::JSTextDecoder>::construct
<LLInt frames>
JSC::Interpreter::executeCall / JSEventListener::handleEvent      (or asyncFunctionGeneratorBodyCall from a microtask)
WorkerMessagingProxy::postMessageToWorkerGlobalScope lambda
WorkerDedicatedRunLoop::runInMode
```

The faulting addresses were data-like (for example `0x0403020100000008`,
`0x0202020202020108`, `0x0303030201010108`, `0x000000007f7f0008`, `0xc`),
so the `DOMWrapperWorld` wrapper table pointer read by `add` appears to be
garbage: the table WebKit uses to map DOM objects to their JavaScript
wrappers looks corrupted. Script running in a page has no way to write to
that native table, which is why the fault is believed to be WebKit's; that
belief is not yet backed by a standalone reduction.

## Why Kandelo is affected

On each process start the host walked the program's export and import
sections and decoded each name with `new TextDecoder().decode(...)`, once
in the kernel worker and again in the new process worker. PHP exports
about 22,000 names, so each PHP process start constructed thousands of
`TextDecoder` wrappers in a burst. Booting the WordPress + MariaDB machine
starts about 22 workers. In 24 of 25 crash reports the faulting thread was
the newest `WebCore: Worker` in the process, handling its first message
from its parent in interpreted code (a Kandelo process starting); in one it
was the first worker created (the kernel worker). No other thread was in
`cacheWrapper` at the time; 17 `Wasm Worklist Helper Thread`s were active
(a large module had just been compiled).

## Workaround and its cost

Wasm name parsing (`host/src/constants.ts`) and the thread-patching export
scans (`host/src/worker-main.ts`) share one `TextDecoder` each.
`decode()` without `stream` keeps no state between calls, so sharing is
behavior-neutral. The cost is negligible; the risk is that other host code
still constructs decoders per call, so a recurrence elsewhere would be
evidence for the hypothesis and a reason to build the reduction, not a
reason to avoid `TextDecoder` as a rule.

## Evidence

Crash rates booting the WordPress + MariaDB machine, Playwright WebKit
webkit-2359 (`26.6`), macOS 27.0.1:

| condition | crashes |
|---|---|
| default | 5 / 32 |
| without the disposable memory-allocation workers | 8 / 32 |
| `JSC_useConcurrentGC=false` | 8 / 32 |
| one shared `TextDecoder` for the name loops | 0 / 32, then 0 / 16 |

So the crash is not the `JSC-BLOCKED-WAIT-GC-STARVATION` deadlock (turning
the concurrent collector off does not avoid it). It also occurred before
the PHP 8.5 upgrade: on pre-#1559 main (PHP 8.3.15) a WordPress + MariaDB
run crashed during boot with the same stack. All 25 crash reports
collected on 2026-10-21/22 have this stack.

Reduction attempts, none of which crashed:

- Before this registry: a page in which a worker creates 60 to 2000 nested
  workers, posts each a shared memory (and in some runs the compiled PHP
  module, a Kandelo artifact, which is why that variant is not kept here),
  and has each construct up to 25,000 `TextDecoder`s in its first message
  handler: no crash in 20+ runs.
- `repro/repro.html` through the driver on 2026-10-22, webkit 26.6, macOS:
  defaults (400 spawns, 20 live, parked children, 100 decoders each), 5 of
  5 attempts `not-reproduced`; `spawns=100&decoders=12500` (25,000
  decoders per child), 3 of 3 `not-reproduced`.

## What is still unknown

The ingredient the reduction lacks. Candidates: module workers
(`{ type: "module" }`, which Kandelo uses for process workers);
instantiating a large Wasm module in the new worker (generated by the page,
not copied from Kandelo); concurrent Wasm tier-up with many
`Wasm Worklist Helper Thread`s active; or Kandelo's own message traffic in
the first handler. A crash with a page that adds those ingredients would
confirm the entry. A Kandelo-side cause would have to corrupt WebKit's
native memory, which page script cannot do directly, but a reduction that
never crashes leaves open that the trigger is some other engine path
Kandelo exercises.

## Removal criteria

The workaround is cheap and behavior-neutral, so it can stay even after a
fix. Retire the entry when either a released Safari containing a fix for a
filed report is the oldest supported Safari, or the investigation shows a
different cause (then reword the tagged comments and the
`docs/browser-support.md` section accordingly).
