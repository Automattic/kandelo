# Grouped syscall completion and visible desktop latency, 2026-11-26

## Scope

The implementation is based on develop `dffcfca5325666d5e02cacdef03d4f14893a4584`.
Its production code is commit `d76c6a9c6d0ce528294883f03f1f746000198716`.
The trigger was a Firefox screen recording in which terminal tiles showed wallpaper for seconds while Foot started. The test uses the actual Sway/SFWBar, Foot and shell packages. WebKit remains experimental.

## What changed

| Owner and lifetime | Work per completion before | Work after |
| --- | --- | --- |
| Rust process image, virtual-to-private-frame translation | Fourteen translations for the fourteen signal words on one page | One translation for a run on one page. Crossing a page rechecks ownership before any store. |
| Rust channel publication | Seven translations for the tested return, errno, signal and status layout | Three translations for that layout. Status is still written last. |
| Rust SDK wait queue, while holding its lock | Validate the chain, then search it for the first matching waiter | Remember the first match during the full validation. A corrupt tail still prevents publication. |
| Host physical memory, while its group exists | Construct typed-array views for individual atomic operations | Use one physical word view per backing. An address outside its prefix triggers a bounds check against the current backing, including growth by a peer. |

The optimization introduces no process or mapping cache, execution transition, ABI message or deferred release. The SDK still controls guest accesses through the page table. Rust selects the physical addresses and the exact waiter. The host holds the WebAssembly memory, and native waits retain their existing pin until settlement.

The order was control, candidate, candidate, control. Each batch had eight rounds. The table gives the median after discarding the first round in each batch.

The desktop measurements start at the first trusted Alt+Return on an already booted desktop with one painted terminal. ## Validation and unsuccessful experiments

- The native runtime-core suite passed 4,101 tests. The final focused memory-group rerun passed 110, including cross-page preflight, duplicate waiters, a corrupt tail and the number of physical reads. The ABI consistency check, TypeScript host build and normal source-only kernel build passed.
- With the develop candidate kernel, real ordinary and grouped SDK runtimes completed 256-thread churn. Forty native-wait exit cohorts reused one backing after exact retirement.
- Removing redundant scheduler tasks produced overlapping or reversed measurements. A separate change to replay frame acknowledgements also failed to improve repeatably. Neither is part of the patch.
- A pixel-checked full-size frame transfer probe found similar Firefox times with ImageBitmap and VideoFrame (5.8 and 5.9 ms). WebKit took 8.0 and 19.6 ms respectively. The existing frame transport stays in place.
- An early WebKit control timed out waiting for five tiles; its screenshot had six prompts. The Chromium desktop guard selected a 1316 × 902 backing and timed out on a glyph threshold calibrated for 2634 × 1806. Neither timeout is a launch time.
- A separate diagnostic captured compositor damage submissions in both engines. Among valid rectangle lists the median summed area was 37.7% of the screen in Firefox (30 lists) and 20.4% in WebKit (34 lists). Four and seven lists respectively covered under 1%. The current display presents full primary frames. Applying damage safely would require preserving pixels across framebuffer rotation, dropped frames, mode changes and color transforms. These observations alone do not establish a presentation speedup.
- The host browser-memory contract suite passed 1,430 tests in 60 files. Ordinary and grouped fork and forty fork/retirement cohorts passed with the SDK's explicit `KANDELO_FICTIONS=mprotect:read_only=accept-unenforced,read_only_max=65536` for that probe. Without its opt-in the existing fixture cannot link its direct calls to `mprotect`.
- The complete Node benchmark command refused to start because the rootfs, PHP/WordPress, and wasm32/wasm64 MariaDB inputs were absent from the isolated projection. Full application benchmarks on both hosts and desktop workload qualification remain acceptance work. The numbers here support the focused adapter and completion results.

Focused tests run through the repository dev shell:

## Where the cursor waited

In a separate traced control run after five painted terminals, each of eight distant positions reached the kernel input device, appeared in Sway's DRM atomic request, and eventually appeared on the cursor plane. The kernel-side timestamps below use the same Worker clock. Each input was matched to the submitted cursor plane's exact horizontal coordinate after conversion from the absolute input range and application of the cursor hotspot. The window separately timed trusted pointermove to cursor pixels. The early pointer-input path can run before the regular DOM pointermove event.

| Median of eight positions | Firefox | WebKit |
| --- | ---: | ---: |
| Kernel evdev delivery to compositor's cursor commit request | 279.7 ms | 88.4 ms |
| Commit request to KMS cursor snapshot | 6.5 ms | 7.6 ms |
| Snapshot to outgoing primary/cursor bundle | 10.2 ms | 7.7 ms |

These runs used separate recording instrumentation and a busy machine. The first interval includes guest scheduling, input handling, graphics work and waits for earlier frames. Its duration cannot be attributed to a single operation. See the [individual matched samples](2026-11-26-grouped-cursor-stages.csv).

A second trace decoded the graphics queries from a sweep. In *each* engine the compositor requested 184 synchronous texture binds, including 92 binds of texture zero, all targeting 2D textures. The acknowledged graphics protocol commits guest binding ownership after native acceptance. A change here needs to preserve failure, context loss, shared contexts, pending commands, and the timing of ownership release. See the [graphics binding contract](../graphics/compatibility-v1.md#acknowledged-c-texturerenderbuffer-bindings-2026-10-24).

Two more experiments were kept out of the product:

- Capturing a 1%, 20% or 40% vertical strip, transferring it to another Worker and drawing into a retained 2D canvas preserved the sampled pixels. Firefox took 6.8 / 8.2 / 9.3 ms, against 6.4 / 6.1 / 6.4 ms for a full bitmap. WebKit took 10.7 / 10.5 / 12.6 ms, against 12.3 / 10.5 / 11.6 ms. This implementation offers little at the observed damage sizes.
- An isolated input transport sent all 92 original PS/2 packets in eight ordered Worker messages while retaining evdev frames. WebKit still took a median of 77.8 ms from evdev to the cursor commit in that run. The Firefox setup missed the five-tile predicate and yielded no comparable sweep.

## Additional checks on the review branch

The develop candidate passed all 55 real-kernel, Worker-boundary and public grouped-session tests with the explicit read-only mprotect fixture opt-in above. The original run without the fixture's opt-in recorded eight link failures. The Chromium guard was also repeated using the repository's exact 97 × 13 Foot prompt mask in **every** tile at a 2634 × 1806 scanout. The control and the candidate both passed all five prompts and all eight cursor positions. Four launches took 3.33 and 3.05 seconds respectively in those single runs.

The clean develop baseline and candidate both ran three rounds of the normal syscall I/O, process lifecycle and empty-filesystem spawn benchmarks on Node and the browser. Both ran the Node WordPress benchmark. The shared-host results were mixed. For example, browser pipe throughput was 34.16 → 25.84 MB/s and Node pipe throughput was 6.83 → 12.85 MB/s. These ordinary-process workloads do not enable the grouped completion path. Browser WordPress requires its composed image. The two MariaDB architectures and full application comparison still require separate qualification.
