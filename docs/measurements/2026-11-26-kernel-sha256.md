# Release kernel SHA-256 throughput

Firefox samples from a Sway terminal launch showed the kernel Worker in SHA-256 rounds while `kernel_exec_commit` revalidated the retained executable. The same profile showed DEFLATE reads during launch and full-frame graphics work during resize. This experiment changes only how Cargo compiles `sha2` for the Wasm kernel package. Every executable read and digest check still runs.

## Packaged kernel comparison

The control was `6b6904b3075437433a1cccec0273142850c8f93c`. Both artifacts came through the source-only kernel package build. The recipe's sole compiler change was `--config 'profile.release.package.sha2.opt-level=3'`. The workspace release default is `s`.

Each browser hashed the same 3,943,708-byte Foot executable through the packaged kernel's `kernel_overlay_activation_codec` streaming SHA-256 entry points. The timer covered initialization, copying 60 KiB chunks through transfer scratch, updating SHA-256 and finalizing it. Compilation, instantiation and result verification were outside the timer. Each engine ran control, candidate, candidate, control with eight hashes per pass. The table gives the median after excluding the first hash of each pass (14 observations per build per browser). Every digest matched Node's independent SHA-256 result.

| Browser on macOS (Playwright) | Control | Candidate |
| --- | ---: | ---: |
| Firefox | 21.74 ms | 11.35 ms |
| Chromium | 20.39 ms | 11.56 ms |
| WebKit | 20.52 ms | 15.63 ms |

The kernel grew from 3,430,219 to 3,431,906 bytes, or 721 additional bytes with gzip level 9. Both modules have the same 120 import and 338 export descriptors. Their SHA-256 identities are `3079c6bdecee1cb1ee13acebeb1751d12bd0a3f5b149d1c5f071a11fdc769d59` and `be0c464bd3e3e2ecd1b40f41bc814e225ef7af1c0b55280064521f854dbf6fcf` respectively.

## Desktop scope

Firefox ran a normal Sway partial shell with a 2634 × 1806 scanout. From one fully painted Foot terminal, the test sent four trusted Alt+Return presses. Timing started at the first keydown. It sampled the primary canvas for prompt text in each of the five tiles, terminal background coverage, and disappearance of the wallpaper. Screenshots recorded the final desktop. Both builds used identical host code, lazy packages and partial image (`8f7a25bc1b93fdb82e2ae78ac0448798d7dfdf22cb63822e6cc1c50bdb997e92`).

In the four-run comparison (control, candidate, candidate, control), the first observation with five painted terminals came at 11.71, 7.22, 25.34 and 42.61 seconds. The 25.34-second run then timed out in the separate cursor observation. Other builds and disk cleanup were active on the machine. These runs establish that the seconds-long delay persists. They cannot quantify an end-to-end gain from the checksum change. The isolated WebKit result measures hashing only. No Safari desktop result was obtained for this change.

## Other trials

- Applying the same compiler override to `miniz_oxide` gave inconsistent inflate results across engines. The shipped recipe retains the default for that crate.
- In the last four seconds of a separate profiled Firefox resize, 208 of 991 kernel-Worker samples were in primary bitmap capture or its pixel readback. Another 130 were in WebGL error-check IPC. These counts describe one Worker's sampled stacks, not elapsed time recoverable from a change.
- Copying the retained 2634 × 1804 WebGL surface to a second 2D canvas before transferring a bitmap increased the Firefox median producer capture from 9.5 to 22.2 ms. The display acknowledged and sampled pixels from each transfer. The candidate also increased total send-to-pixel-acknowledgement time in Chromium and WebKit. This experiment was discarded.
