## 1. Purpose, scope, and the operating constraints

**Goal.** Move every piece of Kandelo *runtime* platform code that can move
from TypeScript/JavaScript into Rust, so that (a) hosts share one
implementation instead of each carrying their own, (b) the logic gets real
type checking, (c) a kernel can be bundled with a VFS such that guest-ABI
changes cannot break images as long as the kernel↔host contract holds, and
(d) the host contract shrinks to the smallest surface a new host author has
to understand.

**Scope: the runtime.** Everything required to run the kernel on a host —
all of `host/src` (kernel worker, the `env` import object, the process-side
worker, both host entries, dynamic linking, scratch/transport, VFS runtime
loaders, device adapters, generated ABI constants), all of
`host/src/fork-*.ts` with `crates/fork-module` + `crates/fork-codec`, and
the runtime boot/session surface of `web-libs/kandelo-session`.

**Out of scope:** build and packaging toolchain (`tools/mkrootfs`,
`images/vfs/scripts`, `scripts/`, `sdk/`, `packages/**`), `benchmarks/`,
and the `apps/browser-demos` UI. `host/test` is not a migration target, but
§9 sizes which of it dies with its subject, because that is real work.

**Operating constraints (maintainer, 2026-09-09):**

- **The whole campaign is one ABI epoch.** Re-instrumentation and package
  rebuilds are available. The ABI and the instrumentation may be iterated.
- **Sound, complete engineering.** No cheats, no hacks, no convenient
  illusion. A boundary is a floor only when it is *proven* to be one.

**On measuring the host contract.** `EXPECTED_HOST_IMPORT_COUNT`
(`crates/host-native/src/lib.rs:77`, currently 84, test-asserted) is a
useful ratchet and its changelog is worth keeping. It is **not the goal**,
and taken alone it misleads: it has gone *up* twice in its own history
(H4 traded five ioctls for one new import, +1), and it would reward the
worst possible move — collapsing thirty imports behind one
`host_do_thing(op, ptr, len)` would score brilliantly while making the
contract opaque and unimplementable. **The goal is the smallest semantic
surface: the fewest distinct concepts a host author must understand and
implement correctly.** §6 measures that directly and uses the count only as
a secondary readout.

## 3. The five structural findings

These are the findings that change what the work *is*, ordered by
consequence. Each is evidence-backed.

### F1 — Process orchestration is implemented twice, in TypeScript

`browser-kernel-worker-entry.ts` (4,847) and `node-kernel-worker-entry.ts`
(4,260) define **54 identically-named functions**. Not helpers — the
lifecycle itself:

```
handleFork  handleVfork  handleOrdinaryFork  handleClone  handleExec
handleSpawn  handlePosixSpawn  handlePosixSpawnResolve  handleExit
handleThreadExit  handleDestroy  containVforkAddressSpace
completeVforkGenerationTeardown  finishVforkDisposition
releaseVforkWorkspace  detachExactProcessGeneration
awaitFinalizedProcessTeardown  finishProcessExit  createFreshProcessMemory
threadAllocatorForLayout  resolveExecutableForLaunch  readExecFromOverlay
parseShebang  bindForkHostImports  dispatchForkHostImport
terminateThreadWorkers  terminatePoisonedKernelWorker  … (54 total)
```

This is the strongest "share code between hosts" result in the census:
**~9,100 lines of process lifecycle written twice, in the language where
parity bugs live**, and it explains why Node/browser parity keeps recurring
as a contract concern. The genuinely host-specific residue is small —
constructing a Worker, constructing a `WebAssembly.Memory`, posting a
message. Everything else is one algorithm.

`parseShebang` is the sharpest instance: it exists **three times** —
`crates/runtime-core/src/exec_target.rs` (exported as
`kernel_exec_target_resolve_shebang`, used *only* by host-native), plus a
hand-rolled copy with its own `MAX_SHEBANG_DEPTH = 4` in each TS entry
(`browser-…:300`, `node-…:1083`). The Rust one already exists and already
works; the two TS copies are pure duplication of POSIX semantics.

### F2 — A complete dynamic linker lives in TypeScript

`dylink.ts` (4,188) + `dylink-fork-archive.ts` (2,152) implement
`dlopen`/`ld.so`: `parseDylinkSection` over the `dylink.0` custom section;
memory and table allocation (`alignUp`, `growMemory`, `growTable`,
`tableAddress`, `functionTableIndex`); symbol scoping and resolution
(`scopedSymbol`, `symbolOwners`, `publishGlobalLibrarySymbols`,
`readDefinedFunctionExports`, `promoteLibraryGlobal`); GOT maintenance
(`refreshGlobalGotEntries`); a dependency graph (`runtimeDependencyNames`,
`appendDependencyScope`); plus the entire dlopen fork-activation state
machine (`DylinkForkState`, `DylinkForkTransactionState`,
`PreparedDylinkForkActivation`, `PendingDlopenTransaction`).

This is loader logic over bytes and tables — deterministic computation with
POSIX-visible semantics.

**CORRECTED 2026-09-09 by the K5 grounding
(`docs/plans/2026-09-09-k5-dynamic-linker-grounding.md`).** This section
originally claimed the floor beneath it was *four* JS-API acts. That was wrong,
and it is the **fifth** inherited "floor" this campaign has disproved — this one
authored here rather than inherited. Walking every `WebAssembly.` site finds
**eight act kinds across 16 call sites**. The four omitted were:
`new WebAssembly.Module`; **`new WebAssembly.Global` plus `Global.value`
get/set** — every GOT cell, and `intl.so` alone forces **2,469** Global
allocations (VERIFIED by `wasm-objdump`); and **import-object construction**,
which is not a plain object but a *stateful counting `Proxy`* whose `get` order
is engine-observable (`dylink.ts:1793-1888`, reasoning at `:1877-1881`).

The verdict is unchanged: all eight have wasmtime-48 equivalents (VERIFIED in
vendored source; `Tag::new` is already used at `guest.rs:5276`), and they
collapse into **one** typed `LinkAct` executor. But the count was asserted from
a symbol overview rather than from reading the call sites, and it was wrong.

It is also a pure portability win: host-native has no linker today, so
`dlopen` on native is unimplemented — moving this to Rust *gains* a
capability rather than merely relocating one.

Related, in `worker-main.ts`: the dlopen reader/writer lock protocol
(`DLOPEN_LOCK_IDLE`/`WRITER`/`MAX_READERS`, with hand-maintained
`DLOPEN_*_OFFSET_WASM32` / `_WASM64` constants), `patchWasmForThread`
(binary rewriting of a wasm module in TS), `encodeStartupMetadata` (a wire
format encoded in TS with its own `STARTUP_E*` errno set), and
`verifyProgramAbi` / `hasCompleteForkInstrumentation` (custom-section
parsing). Each is deterministic computation with hand-maintained
pointer-width duplication — precisely the class Rust's type system
eliminates.

### F3 — The VFS image format is owned by TypeScript, and images are ABI-stamped

The format is written by `tools/mkrootfs` (out of scope, but it is the
writer) and read at runtime by `host/src/vfs/sharedfs-vendor.ts` (3,752)
and `memory-fs.ts` (8,198). `mkrootfs build` takes `--kernel-abi <n>` and
`--abi-snapshot-sha256`, **stamping each image with the exact kernel ABI it
requires**.

Meanwhile `crates/runtime-core/src/sffs.rs` — a 512-line no_std reader for
that same SFFS/VFSI format, ported from `sharedfs-vendor.ts` — is
referenced by nothing but its own `pub mod sffs;` (`lib.rs:46`).

So today the kernel never parses an image; it receives bytes the TS side has
already structured, and image compatibility is pinned to the *guest* ABI.
That is exactly inverted from goal (c). The fix is ownership inversion:

1. **The kernel parses the image** — wire `sffs.rs`. The format then
   versions with the *kernel*, not the guest ABI.
2. **The host supplies only bytes** — `host_blob_read` /
   `host_fetch_archive` is already the correct shape, and `rootfs.rs`
   already consumes base-file bytes that way.
3. **The ABI stamp becomes unnecessary**, because the only versioned
   boundary left is kernel↔host.

`sffs.rs` is therefore not "dead code, wire or delete" — it is the
critical-path enabler for the kernel+VFS bundle. Moving `mkrootfs` to Rust
so writer and reader share one definition is the natural follow-on, but it
is toolchain and out of scope here; the *reader* is the load-bearing half.

### F4 — Rust computes readiness; TypeScript owns waiting (and mirrors kernel state)

`blocked_retry.rs:1` states it: *"Stable kernel-owned targets for
**host-driven** blocking retries."* Rust pins the exact OFD / mqueue
descriptor / SysV id so a numeric fd cannot be reused under a sleeping
retry. Who sleeps, until when, on what wake source, and how request bytes
replay is all TypeScript — 21 of the 68 state containers and ~4,500 lines.

`runSelectKernelAttempt` (`kernel-worker.ts:18957`) lets the kernel compute
readiness, then `resolvePollReadinessIndices` (`:15703`) queries the kernel
for each fd's pipe index and accept-wake index **only so TypeScript can key
its own retry maps**.

**Three separate double authorities** follow from this shape:

| duplicated state | Rust authority | TS shadow |
|---|---|---|
| epoll interest lists | `Process.epolls[].interests` (`process.rs:609`, mutated by `sys_epoll_ctl`, `syscalls.rs:16331`) | `epollInterests` (`kernel-worker.ts:3260`), *"Mirror the change on the host side"* (`:19843`) |
| TCP/UDP endpoint registry + bind conflict rules | `socket.rs` `tcp_can_bind` / `udp_can_bind` / `tcp_register` | `networking/virtual-network.ts` `LocalVirtualNetwork`, `VirtualTcpPeer`, `addrConflicts`, its own errno table |
| listener target selection | `kernel_pick_tcp_listener_target` (exported) | `tcpListenerRRIndex` round-robin in TS |

The epoll mirror has a stated cause at `kernel-worker.ts:12274` —
*"`kernel_handle_channel` crashes in Chrome (V8 shared-memory Wasm bug) for
`epoll_pwait`"* — **RE-VERIFIED 2026-09-09: THE CLAIM DOES NOT REPRODUCE.** It originates in
commit `4131f2498` (2026-04-01, PR #141), whose message says a
*"**suspected** V8 bug"* — the inline comment hardened a suspicion into a
fact. Driving `SYS_EPOLL_PWAIT` through `kernel_handle_channel` on the real
ABI-44 `kernel.wasm` returns correctly on **Node v24.15.0, Chromium
151.0.7922.34 and WebKit 26.5**, on the page main thread *and* inside a
dedicated Worker with a second worker concurrently reading the kernel's
`SharedArrayBuffer` (the production topology), under real cross-origin
isolation, with 2,000 repeat calls and no crash. Evidence:
`docs/plans/probes/2026-09-09-k0c-epoll/`. The mirror is therefore
unjustified and should be deleted. And it is
**not confined to epoll**: reference analysis finds 14 sites across 10
methods, reaching `inheritHostFdMirrors` (fork inheritance),
`#prepareExecFdMirrorPruneWithinKernelEntry` + `#publishExecFdMirrorPrune`
(exec prune via a staged plan), `#rollbackChildHostRegistrationWithinKernelEntry`,
and `finalizePendingChildTermination` (two paths). Removing it touches
process lifecycle, not just epoll.

### F5 — Pure translation layers sitting in the host

`wasi-shim.ts` (1,625) is WASI Preview 1 ↔ POSIX translation: ~180
errno/oflag/whence/filetype constants and eight pure functions
(`translateLinuxErrno`, `wasiOflagsToPosix`, `wasiWhenceToPosix`,
`wasiClockToPosix`, `modeToFiletype`, `posixFlagToWasiFdflags`,
`splitSignedI64Words`, `checkedSignedI64Scalar`). **It requires zero host
capability.** It is a table and a switch, in the one language with no
exhaustiveness checking on either.

**CORRECTED 2026-09-09 by K10 grounding
(`docs/plans/2026-09-09-k10-wasi-shim-grounding.md`).** Two errors above.
(1) `WasiShim` is **not host code** — it runs in the *process worker* on the
**guest's** memory and is wired as the guest's `wasi_snapshot_preview1`
imports (`worker-main.ts:3291-3341`). Its destination is therefore a
**co-resident Rust PIC side module** (the `crates/fork-module` pattern), not
`runtime-core` behind syscall dispatch — that option has no caller, and
routing it through the kernel would need a new channel opcode, i.e. an ABI
addition. (2) It is not "8 functions plus constants": it is **46 guest entry
points**, a **second implementation of the channel syscall protocol** in TS
(`:490-544`, `Atomics.wait`), a preopen table, path resolution, and five
binary struct re-encoders. The "zero host capability" claim **is** verified
(no `host_` in the file; `EXPECTED_HOST_IMPORT_COUNT` untouched; zero `wasi`
in `abi/snapshot.json`). Unrecorded V1 payoff: **`crates/host-native` has no
WASI at all**, so this *gains* native WASI rather than relocating it.

Same class, smaller: `framebuffer/browser-controls.ts` (732) contains
`encodeLinuxMediumRawKeyCode` — the Linux VT input encoding, pure
computation; and `webgl/bridge.ts` (700) decodes a GL command buffer before
issuing calls (the decode is migratable, the calls are floor).

## 5. The recurring shape

```
guest syscall
   │
   ├─► TS pre-dispatch:  marshal variable-length args out of process memory
   │                     into the bounded scratch channel
   ├─► kernel_handle_channel ──► Rust: the POSIX operation (state, semantics, errno)
   └─◄ TS post-dispatch: EAGAIN → park in a TS wait map
                         mmap/brk → update the TS page cache
                         kill/setpgid → route at TS wait maps
                         epoll_ctl → mirror kernel state into a TS shadow
```

Two mechanisms dissolve nearly all of it, and there is no third to invent:

- **Pre-dispatch** → generalize `host_proc_read_bytes` /
  `host_proc_write_bytes` (`wasm_api.rs:251-252`). They exist and are called
  from exactly **six** Rust sites, all in the DRI/GL ioctl path
  (`syscalls.rs:1465-1639`). Two gaps: the signature takes `addr: u32`
  (wasm64 needs 64-bit), and host-native does not implement them today.
- **Post-dispatch** → a Rust-owned blocking scheduler (F4) and a Rust-owned
  mapping table.

## 6. The host contract, measured semantically

All 85 `env.host_*` bindings, grouped by the *concept* a host author must
implement:

| concept | now | target | why |
|---|---|---|---|
| file **names** + metadata | **25** | **0** | the host must open a file; it must not resolve a name. Rust already resolves namespace paths (`resolve_namespace_path_from`, `namespace_lstat_raw`, `syscalls.rs:2075`) |
| graphics / audio devices | 23 | ~8 | genuine device surface; GL already has a command buffer (`gl_submit`) — KMS/GBM/framebuffer can converge on attach + submit + query |
| sockets | 12 | ~6 | byte ops on a host socket. `getaddrinfo` can become a Rust resolver over a host UDP socket → 0 |
| file **bytes** on a handle | 10 | ~6 | genuine floor. `host_append` / `host_append_position` are an O_APPEND atomicity shim that disappears once the kernel owns the file |
| wait primitives | 4 | **2** | `futex_wait`/`futex_wake` are irreducible; `sigsuspend_wait` and `nanosleep` are futex-with-timeout |
| image bytes | 2 | 2 | already the right shape (F3) |
| cross-memory copy | 2 | 2 | irreducible — and **should grow in use** (§5) |
| clock / entropy | 2 | 2 | host services |
| timers | 2 | 1 | one arm-at-absolute-deadline callback; the registry is kernel state |
| guest invocation | 1 | 1 | calling a guest export is host-side |
| host process wait | 1 | 0–1 | native only; no meaning in a browser |
| diagnostics | 1 | 1 | raw byte sink |
| **total** | **85** | **≈31** | of which ~8 are device surface |

The important line is the first: **25 of 85 imports exist only because the
host is asked to resolve names.** That is one concept a host author should
never have to implement, and removing it is the single largest reduction
available — in count *and* in semantics.

Judge progress on the concept column. `EXPECTED_HOST_IMPORT_COUNT` and the
563 constants in `generated/abi.ts` are secondary readouts; the latter is a
good proxy for how much ABI knowledge TS still needs, and should trend to
near zero outside host-capability constants.

## 7. Goal (c): bundling a kernel with a VFS

Today an image is stamped with the guest ABI (F3), so an ABI bump
invalidates images. The end state wanted is: **kernel + VFS ship as one
artifact; the only compatibility surface is kernel↔host.** That requires,
in order:

1. **Wire `sffs.rs`** so the kernel parses the image itself, with the host
   supplying bytes (`host_blob_read` / `host_fetch_archive`). The format
   then versions with the kernel.
2. **Retire the runtime FS authority in TS** — `memory-fs.ts` and
   `sharedfs-vendor.ts` (11,950 lines) stop being the reader.
   `/dev/shm` — currently the one host-backed subtree inside the kernel
   devfs namespace (`syscalls.rs:2068`, `:2122`) — folds into an in-kernel
   shmfs generalized from `tmpfs.rs`, which already has the inode tree, dir
   OFDs, symlinks, rename, statfs, and permission enforcement. (This is
   Workstream H5, whose own text defers it until "SAB-shared `mmap` handled
   in Rust first" — i.e. it is blocked on the mapping-table migration.)
3. **Drop the ABI stamp** once nothing outside the bundle depends on the
   guest ABI, and re-express image compatibility against the host contract.
4. *Follow-on, out of scope:* move the writer (`mkrootfs`) to Rust so
   writer and reader share one definition and can be round-trip tested —
   the standing preference for Rust tooling as an xtask verb.

Step 1 is small and unblocks the architecture. It should go early.

## 8. Goal (a)+(d) in fork: re-deriving the floors under the epoch

The 2026-09-04 **E1 probe** concluded that even with production-site
recording and inline GC provenance, host-side reference logic survives. Two
of its three blockers were *toolchain* limits under a **frozen** guest —
funcref shadow-ordinal threading needs a whole-program transform with
function-signature rewrites; GC struct provenance needs type redefinition
with root-prepend reindexing. **The epoch removes that constraint**, so
those are cost questions now, not feasibility questions.

The third blocker deserves a sharper look, because E1 may have asked the
wrong question.

**E1 asked how to *record* provenance. For GC types it can be *recovered*.**
The one probe-confirmed engine floor is that an *internalized externref* is
not `ref.eq`-comparable (`ref.test (ref eq)` on `any.convert_extern` of a
host externref returned 0 on Node, Chromium, and WebKit). But GC structs and
arrays **are** castable and eq-comparable. A module knows its own finite set
of defined GC types from its type section, so an instrumented module can
carry a generated `ref.test` cascade that discriminates a value's concrete
type at capture time — no provenance table, no weak references, no host side
table. Reconstruction then needs only type + contents, both obtainable in
wasm. Two structurally identical types are indistinguishable, but wasm type
canonicalization makes them the *same* type, so allocating either is
correct.

If that holds, it also closes E1's blocker (b): a **GC-derived** externref
has no broker handle, but `any.convert_extern` on it should return the
original GC object, which *is* discriminable — so its identity is
recoverable in-wasm. The existing probe does not refute this: it tested a
*host* externref, never a GC-derived one.

| P2a in-wasm `extern.convert_any` → `any.convert_extern` identity | 1 | 1 | 1 | 1 |
| **P2b identity after a full HOST round trip** | 1 | **1** | **1** | **1** |
| P2b concrete type still recoverable after host round trip | 1 | 1 | 1 | 1 |
| P2b identity after the host stores it in a JS `Map` | 1 | 1 | 1 | 1 |
| **P2c CONTROL — genuine host externref is `ref.eq`-comparable** | 0 | **0** | **0** | **0** |

**Consequences, now evidence-backed rather than argued:**

1. **E1's blocker (a) — "GC arrays defeat FLOOR-2" — dissolves.** Arrays do
   not need inline provenance because provenance does not need *recording*;
   the concrete type is *recoverable* by a `ref.test` cascade over the
   module's own type section, and contents read back generically. No
   provenance table, no weak references, no host side table, and no
   guest-visible type change.
2. **E1's blocker (b) — "GC-derived externref has no broker handle" —
   dissolves.** Identity survives the round trip through the host, including
   storage in a JS container, and the concrete type is still recoverable
   afterwards.
3. **`ForkGcProvenanceRegistry` (`fork-gc-codec.ts`) is eliminable**, and
   with it the GC/struct/array/i31/static-root host reference surface.
4. **P2c confirms the one real floor stands.** A genuine host externref is
   not `ref.eq`-comparable once internalized — identical to the 2026-09-03
   finding. So **`resolve_externref` (handle → canonical host externref) is
   the single genuine fork reference floor**, and it is irreducible because
   the value is a host object.

Type canonicalization strengthens the result: two structurally identical
declared types *are* the same type, so "which of the two did this come
from" is not a question reconstruction has to answer.

**Scope honesty.** The probes test engine primitives, not the
walrus-injection toolchain, instantiation ordering, or a guest importing the
module's table. Those integration risks are real and unchanged; what is
settled is that no *engine* limit blocks GC reference reconstruction in
wasm.

Independently of the probes, the fork surface has two tracked reductions
already argued in `docs/future-improvements.md`: consolidating the ~43
per-type reference-marshalling `fm_*` exports behind a narrower
encode/decode dispatch, and moving the segmented externref-handle scan out
of `fork-reference-wire.ts` into `fork-codec`. Both belong in this campaign.

## 9. What happens to `host/test`

Not a migration target, but 151,615 lines across 368 files is real work and
should be sized rather than discovered later. Three fates:

- **Dies with its subject.** Tests of TS implementations the migration
  deletes — e.g. `kernel-blocking-retry-snapshot.test.ts` (5,772 lines)
  tests the TS blocking scheduler. Replaced by Rust tests where the
  primitives live, per the fork campaign's own rule.
- **Becomes a Rust test.** Kernel-semantics coverage currently expressed
  through the TS harness.
- **Stays TS.** Genuine cross-host wasm behavior — the 74 fork test files
  (18,959 lines), worker/threading, browser-specific paths. These are the
  reason the TS test suite exists and they must not be traded away.

Classifying the 368 files is a prerequisite for honestly sizing B-K2 and
B-K6, not an afterthought.

## 11. Risks and open questions

1. **P1/P2 are unproven.** §8's conclusion is reasoning from engine
   semantics, not a run. Do not plan on it until the probes report.
2. **The V8 epoll claim is unverified** and sizes K3.
3. **Immediate cross-process shared-memory coherence is an architectural
   limit, not a migration item.** Each pid owns a distinct
   `WebAssembly.Memory`; a store in one is not observable in another and
   futex cannot target a peer's `SharedArrayBuffer`. K7 moves *ownership*
   into Rust. It does not close that gap, and no plan should imply it does.
4. **K7 is hot-path.** Full benchmark suites on Node and browser,
   before/after. No "neutral" claim without numbers.
5. **host-native is a partial host.** It defines the boot/trivial-path
   imports and leaves the rest to `define_unknown_imports_as_traps`
   (`guest.rs:1656`) — 20 `env` registrations plus 9 defines, ~60 trapped.
   So K3/K7 create little native work, while K2, K5 and K9 create real
   native work. Budget it up front.
6. **`syscalls.rs` is 46,885 lines in one file.** Adding four subsystems
   without a mechanical module split first makes it unreviewable.
7. **K4 and K5 are the largest single-step behavior moves in the campaign.**
   Both should use the dormant-flag-then-cutover pattern `tmpfs.rs` proved,
   not a big-bang switch.

## 12. Method and confidence

**Exact** (LSP, reproducible): `kernel-worker.ts` structure via
`find_symbol CentralizedKernelWorker depth=1` — 539 method bodies with
exact spans, 114 properties (68 are `Map`/`Set` containers), class span
2745-34868; every method attributed to a region, none double-counted.
`HostIO` = 83 methods, 5 implementors, 1 production (`WasmHostIO`,
`wasm_api.rs:318`). The 336-export decomposition — 154 TS-only, 35 both,
117 dispatch-only, 26 dead, 2 test-only, 1 native-only, 1 `__abi_version` —
from declared exports intersected against references inside
`dispatch_channel_syscall` (`3960-6444`) and under `host/src`, with the dead
set re-checked repo-wide and against `abi/snapshot.json`
(`find_referencing_symbols kernel_sendfile` → `{}`). The `epollInterests`
blast radius (14 sites, 10 methods) and the 54-function entry duplication
are both name-level exact. The 85 imports and their semantic grouping are
exact.

**Derived, ±10%:** the (b)/(c) split *within* mixed areas — networking,
device adapters, `worker-main.ts`, the VFS remainder. Those interleave
adapter and logic and were apportioned by inspection.

**Reasoned, unproven:** §8's GC type-discrimination argument. Explicitly a
hypothesis with two named probes.

**Not examined:** `host/test` beyond file-level classification;
`binary-resolver.ts` internals (largely toolchain); the `apps/browser-demos`
UI and the build toolchain, both out of scope by direction.

**Supersedes** the two earlier drafts of this file — a grep-only pass, and
an LSP pass scoped to `kernel-worker.ts` and framed against the campaign
plan. This one covers the whole in-scope runtime surface under the epoch
constraint.
